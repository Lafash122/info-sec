## 5. Доработка (если подходящего правила нет)

Выбранный вариант: А

### Вариант А. Собственное правило

Файл правила: [`java-error-handling.yaml`]()

```yaml
rules:
  - id: java-error-handling
    languages:
      - java
    severity: WARNING
    message: >-
      Вывод стека ошибки или сообщения исключения пользователю может раскрыть
      внутреннюю информацию о приложении.
    metadata:
      cwe:
        - "CWE-209: Generation of Error Message Containing Sensitive Information"
      owasp:
        - "A10:2025 – Mishandling of Exceptional Conditions"
    patterns:
      - pattern-inside: |
          try {
            ...
          } catch ($T $E) {
            ...
          }
      - pattern-either:
          - pattern: $E.printStackTrace(...);
          - pattern: System.err.println($E.getMessage());
          - pattern: System.out.println($E.getMessage());
          - pattern: System.out.println($E);
          - pattern: System.err.println($E);
```

Логика правила:
`pattern-inside` ограничивает поиск блоком `try { ... } catch ($T $E) { ... }`. Обёртка `try` важна: без неё Semgrep не матчит `catch` у try-with-resources (в `errorHandlingMethod` используется именно try-with-resources). Тип исключения `$T` - любой, поэтому правило срабатывает и на `SQLException`, и на `Exception`, и на другие типы.
`pattern-either` перечисляет небезопасные способы вывода исключения: `printStackTrace` с любыми аргументами, вывод `getMessage()` или самого исключения в `System.out`/`System.err`.
Метапеременная `$E` связывает перехваченное исключение и объект, у которого вызывается опасный метод, что исключает ложные срабатывания на чужие объекты.

- **Источник:** конструкция `try { ... } catch ($T $E) { ... }` внутри `pattern-inside`
- **Синк:** один из вариантов `pattern-either`:
	- `$E.printStackTrace(...)` - вывод стектрейса;
	- `System.err.println($E.getMessage())` / `System.out.println($E.getMessage())` -  
    вывод сообщения исключения;
	- `System.err.println($E)` / `System.out.println($E)` - вывод всего исключения целиком.
- **Санитайзер:** нет

Результаты запуска правила:

| Версия | Результат | Комментарий |
| --- | --- | --- |
| Уязвимая | TP | нашлось согласно шаблону: в блоке `try-catch`, по шаблону: `- pattern: $E.printStackTrace(...);` |
| Исправленная | TN | заменили в блоке `try-catch` вывод ошибки на проброс исключения с текстом для пользователя |

### 4.1. Как сработало правило (для TP)

- **Источник в правиле:** конструкция `try { ... } catch ($T $E) { ... }` внутри `pattern-inside`

## 6. Выводы

Целевая уязвимость (CWE-209) не была найдена базовым набором `p/java` - это **FN** из-за отсутствия подходящего правила. После написания своего правила `java-error-handling.yaml` уязвимость найдена на уязвимой версии (**TP**) и не найдена на исправленной (**TN**).Побочная находка `p/java`: `formatted-sql-string` в  `DatabaseUtils.java`(CWE-89). По критериям ДЗ она не является TP для целевой уязвимости: другой файл, другой CWE. Кроме того, метод `DatabaseUtils.fetchIds` в текущем коде не вызывается из пользовательских сценариев, поэтому реальная эксплуатируемость этой SQL-инъекции сомнительна и это, скорее, потенциально опасный паттерн, а не подтверждённая уязвимость. В заключение, набор `p/java` хорошо покрывает инъекции, но не покрывает CWE-209. Для полноценного охвата утечек через сообщения об ошибках нужно либо подключать дополнительные наборы правил, либо писать свои.
